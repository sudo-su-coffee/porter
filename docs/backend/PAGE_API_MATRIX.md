# Porter v1.0.0-beta-dev: canonical 39-surface page/API matrix

This is the implementation checklist for the Porter dashboard. A **surface** is a meaningful product page or workflow, not a route alias and not a one-line Vue wrapper. A surface may use a dedicated Vue component, a shared schema-driven resource component, or an intentional tabbed workspace when the behavior is the same.

The matrix is deliberately honest about current coverage. `ResourceManager` is valid for read-heavy CRUD resources, but a page is not considered complete when its backend supports create/update/action behavior that the frontend does not expose.

## Completion rule

The 39 surfaces are complete only when each row has a real frontend caller, a registered backend handler, a matching `routePerms` entry or an explicitly unauthenticated exception, and a truthful persistence/host limitation note. A generic resource screen may satisfy a read-heavy row, but it may not silently omit backend-supported mutations.

## Known non-page limitations

BuildKit Dockerfile/Compose-to-guest conversion remains a separate reviewed conversion worker boundary. Direct microVM boot requires a validated `vmlinux` and `rootfs.ext4` artifact. SSH guest execution is not claimed as supported merely because SSH metadata or certificate endpoints exist. Privileged KVM/TAP and live PostgreSQL migration validation still require an operator host.

## Audit result for this implementation pass

The matrix contains **39 canonical product surfaces**. The dashboard contains **31 genuine Vue view components**, **116 route declarations**, and **40 schema-driven resource routes**; the route count is intentionally larger because several surfaces have nested detail, stream, compatibility, and settings routes. Access-management routes open the real `Teams.vue` RBAC workspace on the appropriate tab instead of using read-only aliases. Secrets, analytics, cron, firewall, feedback, organization events, account recovery, and system events now open real API-backed components or tabs. Environments, environment variables, project domains, project members, persisted settings, source/runtime controls, deployment creation, batch replica operations, historical log loading, and direct artifact readiness now have dedicated real Vue workflows. `ResourceManager` remains responsible only for read-heavy resources or resources whose schema and actions are explicitly declared in the router.

The backend route map also guards custom direct-microVM image upload with the database-seeded `image.upload` permission through migration `0016_image_upload_permission`. Public authentication/health/version routes and authenticated self-service profile/CSRF routes remain explicit exceptions to the central route-permission map; they do not provide an administrator bypass.

The final normalized endpoint evidence report at `docs/frontend/API_ENDPOINT_VIEW_COVERAGE.md` records **311 registered routes, 311 matched Vue source paths, and zero unmatched product routes**. This evidence is supplemented by the method/payload review and the green backend/frontend validation gate; it is not based solely on the existence of router aliases.
